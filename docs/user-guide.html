1.Before you install — the Azure AI Foundry prerequisite

Skill Recorder runs every AI feature on your own Azure AI Foundry resource. Nothing is sent to any other cloud, and the app ships no models of its own. Before (or right after) installing, you need one Foundry resource with three model deployments:

Deployment (default name)Used for
gpt-5.3-codexBuilding skills & automations, and executing skills in the app's runner
gpt-5.2Analyzing recordings (the "what did I do" reconstruction — needs vision)
gpt-4o-transcribeTranscribing spoken narration (only if you use the Narrate toggle)
  1. In the Azure portal / Azure AI Foundry portal, create (or reuse) an Azure AI Foundry resource.
  2. Deploy the three models above. If you pick different deployment names, you'll enter them in the app's connection form later.
  3. Note the resource's endpoint and an API key (portal → your resource → Keys and Endpoint). Pasting the full "target URI" works — the app trims it automatically.
Where credentials live. The key is entered once in the app (or written to ~/.skill-recorder/foundry.json, permissions 0600). It never enters a recording, a skill, or a repository. Advanced/CI setups can use environment variables instead (AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_API_KEY).

2.Installing on a fresh machine

Skill Recorder is published as a source release: one command downloads a pinned Node.js runtime, builds the exact release commit on your machine, and adds a Skill Recorder (Source) app you can relaunch anytime. Nothing is installed globally. Open the project's latest GitHub release and copy the command for your platform — each release pins an exact 40-character commit, shown below as <release-commit>.

Platform support at a glance

PlatformValidated versionsCapture completeness
macOS (primary target) Recent macOS; Apple Silicon & Intel Full: app switches, window titles, browser URLs (Safari + Chromium browsers), clipboard, screen video, narration
Windows Windows 11, x64 & ARM64 (see WINDOWS-VALIDATION.md) Full: window tracking via native APIs, browser URLs via UI Automation, clipboard, video, narration
Linux Ubuntu 22.04 / 24.04 x64 on an X11 session (see LINUX-VALIDATION.md); other distros best-effort Full on X11 (URLs need optional python3-pyatspi and a browser whose accessibility reads aren't blocked — not Ubuntu's snap Firefox; see below); on Wayland: video/clipboard/narration only — window tracking is reported unavailable, honestly, in the app

macOS

commit="<release-commit>"; curl -fsSL "https://raw.githubusercontent.com/microsoft/skill-recorder/$commit/install.sh" | SKILL_RECORDER_COMMIT="$commit" bash
  • Adds Skill Recorder (Source) to ~/Applications — relaunch from Spotlight, Launchpad, or the Dock.
  • To keep the app running after the terminal closes, add SKILL_RECORDER_DETACHED=1 before bash.
  • Works on both Apple Silicon and Intel; the installer verifies every downloaded artifact against pinned hashes.

Windows 11 (x64 and ARM64)

$commit="<release-commit>"; $env:SKILL_RECORDER_COMMIT=$commit; irm "https://raw.githubusercontent.com/microsoft/skill-recorder/$commit/install.ps1" | iex
  • Run in PowerShell. Adds Start Menu and desktop shortcuts.
  • The installer detects your native architecture (x64 vs ARM64) and verifies signatures on downloaded executables.
  • Windows 10 is untested; Windows 11 is the validated target.

Linux (Ubuntu)

commit="<release-commit>"; curl -fsSL "https://raw.githubusercontent.com/microsoft/skill-recorder/$commit/install.sh" | SKILL_RECORDER_COMMIT="$commit" bash
  • The installer is Ubuntu-gated (it checks /etc/os-release) and adds an application-menu entry with the app icon.
  • Required: x11-utils (provides xprop/xwininfo for window tracking) — the installer checks and tells you: sudo apt install x11-utils.
  • Recommended: python3-pyatspi for browser-URL capture: sudo apt install python3-pyatspi (without it, page identity comes from window titles and screen frames — still workable).
  • Start your browser in accessibility mode so URL capture can read its address bar (X11 sessions only — on Wayland, window tracking is unavailable, so URL capture never engages and these flags change nothing): 
    # Firefox (non-snap builds — see the snap caveat below)
GNOME_ACCESSIBILITY=1 firefox &

# Chrome / Chromium / Edge
google-chrome --force-renderer-accessibility &
    Launch the browser this way before recording sessions that involve web pages.
  • Snap Firefox caveat: Ubuntu's default Firefox is a snap, and its AppArmor profile (snap.firefox.firefox (enforce)) lets it appear on the accessibility bus while blocking the tree reads URL capture needs. GNOME_ACCESSIBILITY=1 does not change that — the flag helps non-snap builds. For browser URLs, use a non-snap Firefox (Mozilla's deb or tar build) or a Chromium-family browser with --force-renderer-accessibility. Check compatibility performs a real URL read, so it tells you which case you are in rather than assuming.
  • Session type matters: log in with “Ubuntu on Xorg” for full capture. On Wayland the app still records video, clipboard and narration, and shows exactly which sources are unavailable instead of failing silently.
  • Other distros: not validated; a packaged AppImage can be built from source (npm run dist:linux:x64) and may work, with the same X11 requirements.

3.First launch: permissions & connecting to Foundry

OS permissions (asked once)

PlatformWhat to grant
macOSScreen Recording (System Settings → Privacy & Security) on first launch; Microphone only if you use Narrate; per-browser Automation prompts the first time URLs are read.
WindowsNo OS prompt for screen or window capture; allow Microphone in Privacy settings if you use Narrate.
LinuxNo prompts on X11. On Wayland, the desktop portal asks you to pick a screen when video capture starts. For browser-URL capture, start the browser in accessibility mode — the exact commands are in the Linux install section above (X11 only).

The recorder window shows a readiness panel: an Azure AI Foundry row (your endpoint host once connected) and rows for any capture source that is degraded or unavailable on your setup — if everything is healthy, no warnings appear.

Check your compatibility level

Click Check compatibility in the readiness panel. It inspects your platform, session type, installed tools, and — on Linux — whether a running browser will actually hand over a URL right now (it asks each one for a real read), then reports the level to expect:

LevelWhat it means for your recordings
FullThe richest analyses: app switches, window titles, browser URLs, and screen frames all feed the model.
GoodEverything except live URLs — pages are identified by window titles and screen frames. Fine for most tasks, and analyses stay accurate; the report names the remedy for your case (open a page, relaunch the browser with accessibility on, or — for a snap browser whose reads are blocked — use a different browser).
ReducedNo window tracking (e.g. a Wayland session or missing x11-utils) — only video, clipboard and narration are captured, and analyses of app/web work will be weak. The report names the fix.
  • Every degraded item comes with its copyable fix — a command, a settings path, or a login-screen choice.
  • Full is only reported on live evidence: on Linux, having the prerequisites installed isn't enough — the check actually reads a URL from every running browser and reports Full only if one answers. Being visible on the accessibility bus doesn't count: snap Firefox is visible and still refuses the read. Run the check again after restarting your browser with the commands from section 2.
  • “…but no web page was open to verify a URL read” means the browser is healthy and there was simply nothing to read: a URL can only be verified against a page that is loaded, and a browser sitting on its new-tab page has an empty address bar. Open any website and run the check again — this one is a page load away from Full, not a setup problem.
  • “…but its snap confinement blocks accessibility reads” is a verified result, and it is reported only for browsers that really are snaps (checked against the running process): the browser is up and accessibility is on, and the read was denied anyway. Use a non-snap Firefox or a Chromium-family browser (section 2) if you want URLs; otherwise Good is a perfectly usable level.
  • “…but accessibility reads found no address bar” is the non-snap version: the browser is running unconfined and exposes nothing to read, which usually means it was started without accessibility. Quit it completely — every window, since a second launch just joins the running instance and drops the flag — then relaunch it with the commands from section 2 and re-run the check.
  • Copy report produces a plain-text version (levels, signals, and fixes) — paste it into a support thread and it doubles as the remediation checklist.
  • The AI connection and narration transcription are reported as separate lines — they gate analysis, not capture.

Connecting to your Foundry resource

  1. Record anything short (next section), open the library, and click Analyze.
  2. The connection form appears: paste your endpoint and API key. The three deployment names are pre-filled — change them only if you named yours differently.
  3. Save, then Test connection — expect “Connected — gpt-5.3-codex answered in N.Ns”. A wrong key or missing deployment produces a plain-language error telling you what to fix.

4.Recording a session

  1. Press Record — or ⌘⇧R (macOS) / Ctrl+Shift+R (Windows/Linux) from anywhere.
  2. Just do your task. The app captures app switches, window titles, browser URLs (where supported), clipboard copies, and low-fps screen video with keyframes — locally, in the background.
  3. Optional — Narrate: toggle the microphone (choose your language) and think aloud. Your spoken intent is the strongest signal the analyzer gets. To turn speech into text the recorded audio itself is uploaded to your Foundry transcription deployment — right after you stop, or when you analyze, whichever comes first. With no connection configured, the audio stays on your machine and is simply not transcribed.
  4. The small always-on-top bar shows capture and mic state; mute, switch mics, Finish, or Discard (with confirmation) if the take went wrong.
Recording tips. One task per recording. 30 seconds to a few minutes is plenty. Do the task the way you actually do it — the generalization happens later. If you narrate, say why (“I’m creating a sales order for this customer”), not just what.
Privacy. A recording contains your screen, visited URLs, clipboard text, and any narration. The in-app “What’s recorded” note lists everything. Nothing leaves your machine while you record, and captured signals go to your Azure AI Foundry deployment — and nowhere else — when you click Analyze. The one thing that can be sent earlier is narration audio, which is uploaded to your transcription deployment as soon as the recording stops (if a connection is configured).

5.After recording: Analyze & review

  1. Open the library (sessions list) and select your recording.
  2. Click Analyze. The model reads the timeline and events, looks at screen frames where events are ambiguous, folds in your narration, and produces one intent + ordered steps — typically in 10–20 seconds. When it asks to look at a stretch of the recording it gets every frame captured in that stretch, near-identical ones included, so work that emits no events at all — filling in a form field by field — is still visible to it.
  3. Review it. Edit the title, intent, or any step directly; add, reorder, or remove steps. Or type natural-language feedback (“step 2 was actually about the invoice, not the quote”) and re-analyze — the conversation continues where it left off.

Approve the analysis when it reads right — it is the single input everything downstream is built from.

6.Building a skill or automation

Pick a target

TargetWhat you getWhere it goes
App skillAn on-demand SKILL.md the app itself can execute (next section)Installed into your skill library (~/.skill-recorder/skills) or exported
App automationA scheduled procedure (schedule + step prompts)Saved to your automation library; the in-app scheduler ships in a later release
Copilot Studio skillSKILL.md plus a declarative agent bundle — <name>-agent.zip, connectors.md, and the API spec when groundedExported to a folder you pick — then imported into Copilot Studio (section 8)
Copilot Studio automationautomation.json (trigger + steps) + connectors.mdExported — recreate as a scheduled trigger in Copilot Studio

Optional but powerful: attach an API reference

Turn UI clicks into API calls. On the target picker, attach the application's OpenAPI spec (JSON) — or any docs (md/txt/html) as a best-effort fallback. The builder then grounds action steps in real API operations (“api:createSalesOrder”) instead of describing clicks. Grounded skills carry their spec with them: the app's runner executes the calls, and Copilot Studio imports the spec as a custom connector. YAML specs aren't supported yet — export as JSON (most portals offer both).

Plan → refine → create

  1. The builder proposes a plan: how it generalizes your one example (“one form → all pending forms”), the fixed values it hard-codes (shown as editable pills — URLs, paths, names), the ordered steps with the native tool or API operation each uses, and the allowed tools.
  2. Edit the pills and steps directly, or refine in natural language (“also filter to open items only”).
  3. Create. The final artifact is built from exactly the plan you approved — then installed or exported per the table above.

7.Running skills inside the app

  1. Library → Skills tab. Installed skills are listed with badges: API (carries an API spec) and unrestricted (declared no allowed-tools — every side effect will ask you individually).
  2. Pick a skill, optionally type an input (“Create an order for Contoso: 2× NW-1140”), and Run.
  3. Watch the live transcript. Every side effect pauses for you: shell commands, file writes, and non-GET API calls show a confirmation card — Approve, Deny (the model adapts), or Always allow this kind for this run. The skill's allowed-tools are enforced: commands outside its declared patterns are refused outright.
  4. If the skill asks a question, answer in the inline prompt. Cancel anytime. Every run writes a full transcript to ~/.skill-recorder/runs/ — with credentials redacted.
  5. Deleting a skill. Hover a row in the Skills tab and click the trash icon, then Delete to confirm. That removes the installed skill folder from ~/.skill-recorder/skills/; past run transcripts are kept, and the recording it was built from is untouched (build it again anytime). A skill can't be deleted while it is running — stop the run first.
API credentials for grounded skills. Create a runner.json next to the installed SKILL.md: 
{ "apiBase": "https://your-app.example/api/v1",
  "headers": { "X-Api-Key": "your-key" } }
Credentials stay in this file — never in the skill, never shown to the model, redacted from transcripts.

8.Importing into Copilot Studio

A Copilot Studio skill export contains everything a maker needs:

  1. API-grounded skills first: import api/openapi.json as a custom connector in your environment.
  2. Import <name>-agent.zip in Copilot Studio (or via the Microsoft 365 Agents Toolkit) — it carries the declarative agent manifest, instructions, conversation starters, and detected capabilities (web search / SharePoint knowledge).
  3. Open connectors.md and wire each listed action (e.g. Outlook.SendEmail, or the custom connector's operations) — instructions alone can't grant tools, so this checklist is the manual step.
  4. Test in the Studio chat; the skill's description doubles as its trigger phrasing.
Copilot Studio has no local machine. Skills that need a shell, local files, or a browser on your device belong to the App target. Copilot Studio targets shine for M365/connector/API work — the builder's plans already respect this split.

9.Troubleshooting

First stop for anything capture-related: click Check compatibility — it grades your setup and hands you the exact fix for every degraded item, which resolves most of the rows below without further digging.

SymptomCause & fix
Analysis says “no reconstructable task / no signals”The recording captured no events. Run Check compatibility — expect Reduced with the fix named (install x11-utils, or log in with “Ubuntu on Xorg” instead of Wayland).
“Azure AI Foundry rejected the API key (HTTP 401)”Wrong or expired key — re-enter it in the connection form and press Test connection.
“…could not find the ‘X’ deployment (HTTP 404)”That deployment doesn't exist on your resource — create it in the Foundry portal, or put your actual deployment name in the form's Deployments section.
No browser URLs in recordings (Linux)Install python3-pyatspi, then run Check compatibility — it attempts a real read and names which of the causes applies: no page open (load a website and re-check), no address bar exposed (quit the browser fully and relaunch it with --force-renderer-accessibility, or GNOME_ACCESSIBILITY=1 for Firefox), or a snap browser whose reads AppArmor blocks (flag or no flag — use a non-snap Firefox or a Chromium-family browser). Titles + frames still identify pages without URLs.
“OpenAPI YAML isn't supported yet”Export the spec as JSON from your API portal, or attach the docs as md/txt for best-effort matching.
Skill run refuses a commandWorking as designed: the command falls outside the skill's allowed-tools. Rebuild the skill with broader tools, or run it and approve individually.
Voice wasn't transcribedNarration needs the gpt-4o-transcribe deployment (or your name for it in the form). The audio is kept in the session folder — fix the connection, then re-analyze and it is transcribed then.
HUD bar appears in Linux recordingsKnown limitation: window content-protection is a no-op on Linux. Keep the bar over something non-sensitive.
