Testbed Testing Guide

Step-by-step manual testing with the mock CRUD sales app (tools/testbed) — from a real recording to an executed API-grounded skill. Closes the human halves of gates GJ (documentation levels), GH ③ (Skills-panel run), and exercises G3(C) along the way.

Why this app is a good test. The testbed's HTML UI never calls its own JSON API — the server mutates state directly from form posts. So your recording contains zero API traffic, and any UI→API mapping the builder produces must come from the attached documentation. If it "knows" an endpoint you didn't document, something leaked — that's a finding, not a success.

0.Setup & sanity checks

  1. Skill Recorder installed and connected to Foundry (the connection form saved and Test connection green — this exercises part of G3(C)).
  2. Start the testbed in its own terminal: 
    npm run testbed
    Leave it running. State is in-memory: restarting resets to 4 customers, 6 products, 2 orders — and order numbering back to SO-10003.
  3. Sanity-check both surfaces:
    • Browser → http://127.0.0.1:8787/ shows Home — Northwind Testbed.
    • curl http://127.0.0.1:8787/api/v1/orders → 401 (API is key-gated).
    • curl -H "X-Api-Key: demo-key-123" http://127.0.0.1:8787/api/v1/customers → JSON with 4 customers.
  4. In the recorder, with your browser already open, click Check compatibility — proceed when it reports Full (or Good if you're deliberately accepting the no-URL path). Anything degraded comes with the exact command to fix it.
Two-click bonus check — the URL-readability flip (also the GL2 snap-Firefox experiment). With plain-launched Firefox running, the check should report Good and show the GNOME_ACCESSIBILITY=1 firefox & fix. Quit Firefox fully (snap is single-instance — the flag does nothing while any old window survives), relaunch with the flag, and re-run the check. Two outcomes are both correct, because the check now proves the capability by reading a URL rather than by spotting the browser on the accessibility bus:
  • On Ubuntu's snap Firefox — expect Good with “Firefox is running and accessibility is enabled, but its snap confinement blocks accessibility reads”. That is the verified truth: AppArmor (snap.firefox.firefox (enforce)) permits the bus name and denies the tree reads, so no launch flag can reach Full. Recordings still identify pages by title and frames.
  • On a non-snap Firefox (Mozilla deb/tar) or a Chromium-family browser started with --force-renderer-accessibility — expect Full with “… — URLs verified by a live read ✓”. This is the real path to Full, and the only one that gives your Part A baseline real browser.url events.
Record both readings — they're checklist row 12.

Seeded data you'll reference throughout: customers Contoso Ltd (CUST-1001), Fabrikam Inc, Adventure Works, Tailspin Toys; products include NW-1140 (Chai Tea Chest, $18) and NW-2207 (Cajun Seasoning, $22).

A.Make the baseline recording

One recording backs the whole experiment. Start the recorder (⌘⇧R / Ctrl+Shift+R), then do exactly this in your browser and nothing else:

  1. Open http://127.0.0.1:8787/ (Home).
  2. Click Customers — note Contoso Ltd is CUST-1001.
  3. Click Products — note NW-1140 ($18) and NW-2207 ($22).
  4. Click Orders, scroll to New order.
  5. Choose customer Contoso Ltd (CUST-1001).
  6. Row 1: product NW-1140 · Chai Tea Chest, quantity 12.
  7. Row 2: product NW-2207 · Cajun Seasoning, quantity 3.
  8. Leave row 3 empty, press Submit order — you land on Order SO-10003, total $282.00.
  9. Stop the recording.
Narration (optional but recommended once): repeat with Narrate on, saying things like "I'm creating a sales order for Contoso." — it tests the transcription deployment and gives the analyzer the intent directly.

B.Analyze it & what to expect

  1. Library → select the recording → Analyze.
  2. PASS looks like: an intent about creating a sales order for Contoso in the Northwind app, with ordered steps covering browsing customers/products, filling the order form (both line items, quantities 12 and 3), and submitting — page identity via the page titles ("Orders — Northwind Testbed" …).
  3. FAIL looks like: "no reconstructable task / no signals" — a capture problem, not an analysis problem. See Troubleshooting.
  4. Approve (edit anything that reads wrong first).

C.The documentation-level experiment

Four rounds over the same approved analysis. Each round: on the target picker, attach one file from tools/testbed/docs/ under API reference (optional) → build an App skill → inspect the proposed plan → note the outcome → remove the reference before the next round. (Attaching or removing resets the builder's conversation — that's by design; just build again.)

RoundAttachExpect in the planFailure signs
L1 full specopenapi-full.json Action steps grounded as api:listCustomers / api:getCustomer and api:createSalesOrder; no click/browser/navigate language; base URL hoisted into an editable value. UI-replay steps; an operationId that isn't in the spec.
L2 minimal specopenapi-minimal.json Same grounding via synthesized ids — expect api:getCustomers and api:postOrders (or the api:POST /orders route form). Ids copied from L1 (e.g. createSalesOrder — that name doesn't exist in this spec).
L3 prose docsapi-guide.md No api: refs at all (docs can't be machine-verified) — but steps written against the documented HTTP endpoints in prose ("POST {{base}}/orders with customerId and items[].sku/quantity", tool web_fetch), not UI replay. Fabricated api: refs (fake grounding), or pure UI-replay that ignores the docs.
L4 partial specopenapi-partial.json Customer/product lookups grounded (api:listCustomers…) while the order-create step honestly falls back to the web UI/form — orders aren't in this spec. A hallucinated api:createSalesOrder; or refusing to plan at all.
The universal red line — credentials. In every round, the plan, values, and SKILL.md may name the scheme ("requires the X-Api-Key header / apiKeyAuth") but must never contain demo-key-123. If the literal key appears anywhere, record it and stop — that's a leak.

Quick extra: the YAML refusal

Try attaching any .yaml file. Expect the exact message: "OpenAPI YAML isn't supported yet — export the spec as JSON (most API portals offer both), or attach it as docs for best-effort matching."

D.Run a skill against the testbed (gate GH ③)

Two ways to get a runnable skill — do at least one:

  • Full loop (best): in round L1, continue past the plan — Create the App skill and install it to your library.
  • Fixture shortcut: copy the committed fixture evals/fixtures/runner-sales-skill/ into ~/.skill-recorder/skills/ (its name is runner-sales-order-demo).
  1. In the installed skill's folder, create/edit runner.json: 
    { "apiBase": "http://127.0.0.1:8787/api/v1",
  "headers": { "X-Api-Key": "demo-key-123" } }
  2. Library → Skills tab. Expect the skill listed with an API badge (and no "unrestricted" badge — it declares its allowed operations).
  3. Input: Create an order for Fabrikam: 5x NW-1140 and 2x NW-2207 → Run skill.
  4. Expect, in order:
    • a transcript entry calling api:listCustomers and resolving Fabrikam's id;
    • a confirmation card — "Call createSalesOrder (POST /api/v1/orders)" with a collapsible detail view. Approve it;
    • HTTP 201 in the transcript and a final summary naming the new order id;
    • the footer shows Transcript: <path>.
  5. Verify the side effect is real: open http://127.0.0.1:8787/orders — the new order exists for Fabrikam with those quantities.
  6. Verify redaction: open the transcript file and search for demo-key-123 — zero occurrences.

Negative tests (do both)

  1. Deny path: run again, and this time Deny the create-order card. Expect the model to adapt gracefully (report it couldn't complete, no order created — check /orders) rather than error out.
  2. Cancel: start a run and press Cancel run mid-flight. Expect a clean stop; starting another run afterwards works. (While one run is active, a second start is refused with "A skill is already running.")

E.Optional: the Copilot Studio bundle

  1. From the same analysis, with openapi-full.json attached, build a Copilot Studio skill and export it to a folder.
  2. Inspect the folder: SKILL.md, declarativeAgent.json, manifest.json, color.png + outline.png, connectors.md (with a Custom connector section pointing at the spec), <slug>-agent.zip, and api/openapi.json.
  3. If you have a Copilot Studio environment (gate GG ③): import api/openapi.json as a custom connector, then import the zip, wire the actions per connectors.md, and test in the Studio chat. A schema-version rejection is a finding to report — the fix is bumping two pinned constants.

Troubleshooting

SymptomFix
Port 8787 busyPORT=8790 npm run testbed — then use that port everywhere, including runner.json.
Analysis found no signals (Linux)Run Check compatibility — expect Reduced with the named fix (Wayland session or missing x11-utils). Use an "Ubuntu on Xorg" session.
No browser.url events (Linux)Check compatibility tells you which, from a real read: missing python3-pyatspi, no browser running with accessibility on, or a snap browser whose reads AppArmor blocks (the card above — use a non-snap Firefox or Chromium for URLs). Page titles + frames still carry the test either way.
Skill run fails with HTTP 401runner.json missing or wrong key/path — it must sit beside the installed SKILL.md.
Skill run fails with "could not reach…"The testbed isn't running, or apiBase doesn't match its port.
Order totals look wrongRemember the seed: NW-1140 is $18, NW-2207 is $22 — 12×18 + 3×22 = $282.
Order id isn't SO-10003Fine — numbering continues while the testbed stays up; restart it to reset state.
